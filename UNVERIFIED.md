| 14 | How often the rewriter changes a prompt in a way the judge calls worse | **Open, reduced but not closed.** On the 1.0.0 system prompt a first 8-sample run (50 prompts, 400 samples, uncommitted) had 19 worse (4.75%), and two runs with the final harness (416 samples each) had 16 and 18, so 34 of 832 (4.1%). The worse samples sit in four prompts: `non-english-de` ("Tests dafür" became "Tests für beides"), `long-3500` and `edge-max` (in a long list, "never show it again after that" became "after it is skipped or completed") and `emphatic-3` ("anywhere" narrowed to "anywhere in the README"). In each the rewriter settled something the developer left open, and the guard does not catch it. Twins of the two long lists that state the tail explicitly (`long-3500-clear`, `edge-max-clear`) had 0 worse of 64 samples across four runs, so long lists are handled and the failures are those phrases. **The applied sentence** (keep references as open as written, and a place named in one request does not narrow "anywhere" in another) took the 832 samples of two final-harness runs from 34 worse to 22 (2.6%, one-sided p 0.067): the four prompts went from 33 of 64 worse to 17 of 64 (`non-english-de` 12 to 7, `long-3500` 8 to 4, `edge-max` 8 to 3, `emphatic-3` 5 to 3), but they are the prompts it was written against, so that is in-sample. Everywhere else it went from 1 worse of 736 to 5 (`vague-3` dropping "a bit", `multi-2` narrowing "write tests", `long-500` turning "I suspect" into "the developer suspects"), which may be a cost of the sentence or noise. Other wordings were measured in scratch copies and not applied: one keeping only broad words as written (14 of 400 worse and `image-1` reverted 8 of 8), a broader one (9 of 400), and a sentence in the list rule (11 and 8 of 400, the same as the applied wording, though it removed the `non-english-de` failures: 0 of 16 against 5 of 16). Three fresh prompt sets could not separate the wordings, because the defect only shows on specific prompt shapes. A wording that named README in capitals fails the prompt style test, so the applied one says "readme". The release bar is not met. |

Nothing else blocks use. Two limits remain by design, listed at the end.

## Not verifiable

- The exact status the API returns when a balance is empty (item 7) stays unobserved by design; the classifier does not depend on it.
- The 2025-11-10 `claude.com` blog post on prompt engineering and the Console prompt tools' own docs were read only through a summarizer, so their quotes in `docs/research-notes.md` are unconfirmed. Neither changes a rule: the platform docs win where they differ.
- Whether CI can run `tsc -p .`. On 2026-10-19 `claude plugin validate --strict .` and `claude plugin test .` were run on a copy without `.claude-plugin/types/` and neither wrote it, so `verify` leaves type errors and `evals/*.ts` unchecked. Run `tsc -p .` locally before a PR (item 11).
- Whether `claude plugin marketplace add monte3l/m3l-prompt-optimizer#<tag>` pins the plugin files of a `"./"` source. The Claude Code docs describe the `#ref` form for the catalog but do not state it for plugin content.
- Whether an installed plugin and a `--plugin-dir` copy of the same name can load together is undocumented. Do not run both.
- The rewriter's three examples have no outer `<examples>` tag, which the best-practices page recommends for several examples. Changing it is a system-prompt edit that needs a before and after eval, so it is a candidate for after 1.0.0.
